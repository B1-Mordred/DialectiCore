# /goal — Multi-AI Talk Show Production Platform

## 1. Objective

Implement a self-hostable, Docker-based production platform that automatically creates complete talk-show episodes in which multiple independently configured AI models participate in a real, turn-by-turn discussion.

One AI participant is designated as the host/moderator. The host must actively manage the discussion, react to prior answers, challenge claims, nominate speakers, request clarification, identify disagreements, and close the episode.

After a subject and production configuration have been defined, the system must be able to execute the complete production sequence:

1. Validate the episode definition.
2. Research the subject and create an evidence pack.
3. Prepare the host and AI participant roles.
4. Conduct a genuine multi-model discussion.
5. Validate and edit the transcript without changing its meaning.
6. Produce localized language variants.
7. Generate speech through a remote Voicebox server.
8. Generate character video, reaction shots, studio shots, B-roll, and graphics through a remote ComfyUI server.
9. Build a synchronized audiovisual timeline.
10. Render a complete video with FFmpeg.
11. Run automated quality-control checks.
12. Provide preview and approval workflows.
13. Export a YouTube-ready video and associated metadata.

The system must support a configurable episode duration and a configurable set of output languages.

The entire system, including model endpoints, workflows, voices, characters, language behavior, generation presets, queues, retry policies, storage, quality thresholds, and production settings, must be manageable through a Web UI.

## 2. Fundamental Design Principles

### 2.1 Real multi-agent discussion

The discussion must not be generated by a single model in one prompt.

Each participant must be an independently configured agent using its own:

- Model endpoint
- Model ID
- System prompt
- Perspective
- Expertise profile
- Speaking style
- Private discussion memory
- Sampling configuration
- Tool permissions
- Voice
- Visual character profile

Each response must be generated only when it is that participant's turn.

Every participant receives:

- The shared evidence pack
- The public discussion transcript
- The current discussion phase
- Remaining time budget
- The latest host instruction
- Its own private memory

Participants must not receive the private memory, future plans, or hidden reasoning of other participants.

### 2.2 Durable and resumable production

The episode must be implemented as a durable workflow consisting of independently restartable stages.

A failed video segment, TTS request, translation, or final render must not require restarting the full episode.

Each stage must be:

- Idempotent where practical
- Persisted
- Retryable
- Auditable
- Cancellable
- Observable
- Restartable from its last valid checkpoint

### 2.3 Canonical transcript

The completed source-language discussion is the canonical editorial source.

All downstream content must link back to canonical discussion turns:

- Localized dialogue
- Audio
- Video
- Subtitles
- Citations
- Timeline segments
- Rendered scenes

Post-processing must not silently introduce new factual claims or stronger arguments.

### 2.4 Remote media services

ComfyUI and Voicebox are remote services.

The platform must not assume that either service is installed locally.

Both integrations must use configurable adapters with:

- Base URL
- Authentication
- Timeouts
- Retry policy
- Concurrency limits
- Health checks
- Capability discovery where supported
- Job submission
- Job status polling or event monitoring
- Result retrieval
- Cancellation where supported

### 2.5 Provider-neutral AI integration

The platform must support local and remote model providers through a common internal interface.

Initial supported provider types:

- OpenAI-compatible API
- Ollama
- Anthropic-compatible API
- Mistral-compatible API
- Generic configurable HTTP adapter

The architecture must allow additional providers to be added without modifying the discussion engine.

## 9. Research and Evidence Pack

### 9.1 Research process

The research worker must:

1. Convert the central question into research sub-questions.
2. Identify required factual dimensions.
3. Retrieve relevant sources through configured tools.
4. Prefer recent and authoritative sources when appropriate.
5. Store source metadata.
6. Extract claims.
7. Associate claims with supporting or contradicting sources.
8. Identify uncertainty and disagreement.
9. Produce a structured evidence pack.

### 9.2 Evidence pack structure

```json
{
  "topic": {},
  "definitions": [],
  "verified_facts": [],
  "supported_claims": [],
  "uncertain_claims": [],
  "disputed_claims": [],
  "competing_interpretations": [],
  "important_statistics": [],
  "source_index": [],
  "suggested_discussion_dimensions": [],
  "fact_check_rules": []
}
```

### 9.3 Participant access

All participants receive the same public evidence pack.

Participants may receive role-specific reading priorities, but no participant may receive falsified or selectively altered evidence.

### 9.4 Tool usage during discussion

Participants may optionally use tools during the discussion when permitted.

Initial tool support:

- Web search
- Web page retrieval
- Calculator
- Evidence pack lookup

Tool usage must be logged and subject to time and cost limits.

## 10. Real Discussion Engine

### 10.1 Discussion phases

Implement configurable phases:

1. Introduction
2. Opening positions
3. Main discussion
4. Focused challenge
5. Closing statements
6. Host synthesis

Each phase has:

- Time allocation
- Required outputs
- Allowed turn types
- Host behavior
- Completion conditions

### 10.2 Host responsibilities

The host must:

- Open the episode
- Introduce participants
- Define the subject
- Ask context-sensitive questions
- React to actual answers
- Identify disagreements
- Ask participants to answer each other
- Request evidence or mechanisms
- Prevent repetition
- Balance speaking time
- Track uncovered dimensions
- Manage remaining duration
- Close discussion branches
- Summarize agreements and disagreements
- Deliver a final synthesis

The host must not be provided with future participant responses.

### 10.3 Participant behavior

Participants must:

- Respond to the actual preceding discussion
- Maintain their assigned analytical perspective
- Use the shared evidence pack
- Distinguish facts, inference, opinion, and prediction
- State disagreement plainly where warranted
- Avoid agreement merely for politeness
- Ask other participants questions
- Admit uncertainty
- Revise positions when persuaded
- Avoid repeating previously covered content

### 10.4 Structured turn output

Each participant response must use structured output.

```json
{
  "spoken_text": "I agree with the productivity argument, but...",
  "intent": "rebuttal",
  "responding_to": "turn-id",
  "claims": [
    {
      "text": "Claim text",
      "claim_type": "supported",
      "confidence": 0.78,
      "evidence_refs": ["source-id"]
    }
  ],
  "questions_for_others": [
    {
      "participant_id": "participant-id",
      "question": "Question text"
    }
  ],
  "requested_follow_up": true,
  "private_memory_update": {
    "unspoken_points": [],
    "open_questions": [],
    "position_summary": ""
  }
}
```

Validate the schema before accepting the turn.

If parsing fails:

1. Attempt structured repair.
2. Retry the same participant with a correction prompt.
3. Fall back to plain text only if configuration permits.
4. Record the repair attempt.

### 10.5 Speaker selection

Implement a deterministic discussion controller.

Candidate score:

```text
speaker_score =
    relevance_to_current_question
  + unresolved_disagreement_weight
  + requested_response_weight
  + expertise_match
  + underrepresented_speaker_bonus
  - recent_speaking_penalty
  - repetition_risk
  - duration_overrun_risk
```

The host may nominate a participant, but the controller may override invalid or unfair selections.

### 10.6 Speaker balance

Track:

- Total turns
- Total words
- Estimated speaking seconds
- Actual speaking seconds after TTS
- Number of interruptions
- Number of unanswered questions
- Recency of last turn

Expose balance in the Web UI.

### 10.7 Discussion memory

Maintain:

#### Public memory

- Transcript summary
- Current topic
- Covered topics
- Agreements
- Disagreements
- Open questions
- Claims needing fact-checking
- Remaining duration

#### Private participant memory

- Current position
- Unspoken arguments
- Questions for others
- Claims to challenge
- Previous concessions
- Preferred future intervention

#### Host memory

- Agenda
- Coverage status
- Speaker balance
- Repetition indicators
- Unresolved disputes
- Remaining time
- Planned closing synthesis

### 10.8 Context management

Do not resend the complete raw transcript indefinitely.

Implement layered context:

- Latest turns verbatim
- Older discussion summarized
- Current topic state
- Relevant claims
- Participant private memory
- Evidence references

Store summaries with versioning and preserve the raw transcript separately.

## 11. Configurable Episode Duration

### 11.1 Duration values

Each episode must define:

- Target duration
- Minimum duration
- Maximum duration
- Maximum optional extension
- Maximum monologue duration
- Phase allocation percentages

### 11.2 Runtime estimation

Before audio generation:

```text
estimated_seconds = word_count / configured_words_per_second
```

Configure expected speaking rates per language and voice.

After TTS:

- Replace estimates with actual audio durations.
- Recalculate episode duration.
- Rebuild timeline timing.

### 11.3 Soft and hard controls

Soft controls:

- Inform host of remaining time.
- Encourage shorter answers near the limit.
- Move toward closing phases.

Hard controls:

- Prevent new low-priority discussion branches.
- Limit response length.
- Skip optional turns.
- Enforce maximum duration.
- Preserve the closing summary budget.

### 11.4 Duration correction after TTS

When too short:

- Restore approved optional turns.
- Add a host recap based only on existing discussion.
- Extend transitions modestly.
- Add approved supporting visuals with silence only where editorially acceptable.

When too long:

- Remove low-value redundant turns.
- Regenerate selected turns more concisely.
- Shorten transitions.
- Remove optional B-roll pauses.
- Apply very small audio time correction only as a last resort.

Do not globally speed up or slow down the episode enough to produce unnatural speech.

## 12. Transcript Processing

### 12.1 Raw transcript

Store exactly:

- Every accepted generated turn
- Model identity
- Participant identity
- Provider metadata
- Prompt version
- Response metadata
- Tool calls
- Citations
- Timing
- Retry history
- Moderation actions

### 12.2 Broadcast transcript

Create a lightly edited transcript.

Allowed edits:

- Grammar correction
- Removal of accidental duplicated phrases
- Removal of malformed fragments
- Pronunciation markup
- Removal of dead-air responses
- Clear correction of transcription artifacts

Disallowed edits:

- New factual claims
- Stronger arguments
- New conclusions
- Reordering that changes meaning
- Assigning statements to another speaker

Every broadcast turn must retain source turn references and an edit type.

### 12.3 Semantic validation

Use a separate validator model and deterministic checks.

Store:

- Semantic fidelity score
- Added claim detection
- Removed claim detection
- Contradiction detection
- Speaker attribution check

Block downstream production when configured thresholds are not met.

## 13. Multilingual Production

Implement three localization modes.

### 13.1 Independent discussion

Run a new discussion in the target language.

Use when each language version may differ editorially.

### 13.2 Direct translation and dubbing

Translate the canonical transcript and preserve exact turn order and meaning.

This should be the default first-release mode.

### 13.3 Localized re-performance

Ask the original participant model, or an equivalent configured model, to express the same turn naturally in the target language.

Requirements:

- Preserve semantic content
- Preserve claims
- Preserve speaker intent
- Preserve turn order
- Do not add new claims
- Validate fidelity

### 13.4 Localization output

For each localized transcript turn store:

- Source canonical turn
- Localized text
- Translation mode

## 29. Acceptance Criteria

The implementation is complete when all of the following are true.

### Discussion

- A user can configure one host and at least three AI participants.
- Participants may use different model providers.
- The discussion is generated one turn at a time.
- Each participant has private memory.
- The host responds to actual prior statements.
- Participants can disagree, ask questions, and revise positions.
- Speaker balance is tracked.
- Episode duration is configurable.
- The discussion stops within configured duration limits.
- Every turn is persisted with model metadata.

### Transcript

- Raw and broadcast transcripts exist.
- Broadcast edits retain source turn links.
- Semantic fidelity is checked.
- A user can regenerate or remove an individual turn.
- Transcript approval can block downstream production.

### Languages

- A source language can be defined.
- Multiple output languages can be selected.
- Translation and localized re-performance are supported.
- Localized turns retain source links.
- New claim detection is implemented.

### Audio

- Voicebox is configurable as a remote service.
- Audio is generated per turn.
- Voice profiles are reusable.
- Actual duration is recorded.
- Individual failed turns can be regenerated.
- Audio QC is recorded.

### Video

- ComfyUI is configurable as a remote service.
- Workflow templates are versioned.
- Character profiles are reusable.
- Per-turn talking-head video is supported.
- Reusable reaction and idle loops are supported.
- Failed visual generation has fallback handling.
- Visual QC is recorded.

### Rendering

- A timeline is built from transcript, audio, and video.
- The timeline can be edited.
- A preview can be rendered.
- A final video can be rendered with FFmpeg.
- Subtitles are available.
- Final runtime is validated.
- Final QC is recorded.
- A YouTube package is exported.

### Operations

- All administration is available through the Web UI.
- Workflows are resumable.
- Failed stages can be retried.
- Workers can restart without losing production state.
- All major actions are audited.
- Credentials are not exposed in normal API responses.
- Health status is visible.
- Backups and restore procedures are documented.
